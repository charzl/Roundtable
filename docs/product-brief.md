# 产品需求与讨论交接

## 已确认的用户意图

- 应用名称：圆桌会议（Roundtable）。
- 当前专注简单、可用的 macOS 桌面应用，先在 Mac mini 上运行。手机 App、云端和远程接入暂缓，不因这些远期方向启动 Swift 重写。
- 用户在统一的会议窗口提出问题，Claude、Codex、AGY 等参会者都能看到。
- 参会者能看到其他参会者的公开发言，互相回应、提问和反驳，模拟真实会议。
- 支持持续讨论，不限于多个模型各回答一次。
- 讨论形成方案和总结后，用户仍可在同一会议中连续追问。系统可推荐一位参会者回答，用户也可指定其中某一位；回答者须获得原会议和后续追问上下文。开发代码已加入，真实 Organizer 调用仍待验证，规则见下文。
- 提供两种模式：逐轮共同讨论，以及同题并行独立调查、统一公开后对比讨论。独立调查算第 1 轮，总轮数仍最多 10；创建会议时选择 Leader（会议负责人），Leader 在结束时汇总所有参会者意见，负责最后的 summary。详细规则见 [分开调查模式设计](independent-investigation-design.md)，核心流程已实现，验收见下文。
- 语言可选中文、English、随系统，默认随系统，并预留更多语言包。界面语言与回答语言分别设置；回答默认「用提问者的语言回答」，明确语言要求优先，同批独立调查固定要求。切换界面语言保留原始发言与证据。详细规则见 [多语言设计](localization-design.md)，核心流程已实现，验收见下文。
- 同一时间只有一位人类或 agent 公开发言；agent 可以并行研究和分析，再将公开结果带回会议。
- 最多讨论 10 轮，能形成可供用户判断的结果时可以提前结束；到上限必须交付有依据的折中方案，或 pros and cons 与剩余分歧，由用户决定，不自动延长。
- 各方关键观点有迹可查，保留来源、分析方法、必要输入、研究产物、验证结果和修正记录；总结也应引用这些依据并保留异议。
- MCP 配置和 skills 尽量统一维护与共享；共享目录不等于已加载或可调用，各运行时的实际能力和授权仍需验证。研究成果应能复用与交叉核查。
- 自行开发的代码选择 Apache License 2.0；它允许商业使用与闭源衍生，并非逐次授权使用的许可。复用代码保留原许可和版权声明。
- 独立于 BabyLog 开发；原 BabyLog 会话继续讨论 BabyLog。

## 概念边界

模型负责推理和生成回答。Agent 是使用模型的参会者运行时，具有身份、角色、上下文和可选工具。Claude Code、Codex、AGY 是潜在的接入入口；具体模型与可用接口需核实当前配置和官方文档。

圆桌会议负责公共会议记录、消息分发、发言调度、参与者状态和用户控制。不要假定这些入口自动共享当前聊天或彼此上下文。

## 第一版建议，尚待在新项目讨论

- 本地会议服务与界面分开，为以后手机接入保留接口。
- 公共会议记录保存人类和各 agent 的公开发言，保留身份与时间。
- 先独立发言，再围绕彼此观点讨论；用户随时插话、暂停、点名或结束。
- 自由讨论允许自主选择回应对象；发言调度有轮次、并发和费用上限，避免无限相互触发。
- 显示真实连接状态，包括未登录、等待授权、运行中和失败；演示数据与真实模型输出明确区分。
- 会议记录可回看，结论区分共识、分歧与待验证事项。
- 初期工具权限以讨论为主，写文件、运行代码等能力单独设计。

macOS 桌面产品形态已确认。用户授权开始开发后，第一版采用 Electron 界面、独立 Node.js 本地会议服务和真实 CLI 适配器。默认使用本机已有登录；模型可在创建会议时指定，费用依参会者账号。API 接入、手机界面与远程认证仍待设计。

## 会后追问（开发代码已实现，真实接入待验证）

用户要求形成方案后继续 follow up，由系统选择合适的一位参会者，或由用户指定原参会者之一回答。用户随后明确不需要独立 follow-up 页面；开发代码已合并为 Discussion 的同一个持续输入框。总结后仍在这里提问，由系统分配或用户点名一位原参会者回答。以下规则已实现，验收及真实接入限制见 [Organizer 与追问验收](organizer-verification.md)。

- 总结后继续使用 Discussion 的原输入框，每次用户提问只触发所选参会者的一次回答；不自动重新启动全体讨论，也不自动增加原会议轮数。
- 初次讨论结束由 Leader 产生总结；用户继续追问时，中间过程可以不产生新总结。问完后由用户点击 Summary（总结与决定）里的「重新生成总结（Regenerate summary）」按钮；Discussion 不重复设置按钮或新增标签页。每次 Leader 都读取截至当前的全部公开聊天记录，包括原讨论、后续问答、修正和证据，生成新版本，旧稿保留。单个回答不自动当作全体共识，未回答或失败的问题仍保留为未知项。
- 提供「自动推荐」及手动选择原参会者。用户所说「最赞成」可能指最支持选定方案的参会者，也可能指用户最认可的参会者；自动模式建议结合对用户选定方案的明确立场、对追问主题的实际分析和证据，手动模式直接保留用户选择。推荐依据须引用实际公开发言，无法判断时明确说明并建议 Leader，不虚构支持度。
- 每次调用提供原始题目、公开讨论、已公开调查报告、所依据的总结版本、用户已保存的决定、证据与会后问答。切换回答者也能衔接上下文，不依赖某个 CLI 自动记住之前调用。
- 保存提问、回答者身份、推荐依据或用户点名、所依据的总结版本及真实调用附件。只有取得有效 provider 输出才显示为回答；调用失败保留状态，重试或换人须明确记录。
- 原会议结论与用户决定保留原版本，追问回答不自动覆盖，也不冒充全体共识。若追问改变方案，可另由用户发起重新讨论或生成新版本总结。
- 自动模式以此前实际回复为依据：延续同一问题时优先保持上一位回答者，引用其他人的观点或转向其他分析时重新选择。不得只因一个参会者赞成某方案，就把其意见标为更正确；追问涉及风险和反例时，应保留并利用原有异议。

### 问题 dispatcher（由 Organizer 执行）

用户明确要求根据参会者之前的回复判断追问给谁。使用「明确规则 + 上下文语义选择」：

- 用户点名或点击某条发言的「追问」，直接选该作者；若该作者当前无法调用，明确提示，不静默换人。
- 未明确指定时，选择器读取当前问题、近期会后问答、最终方案和相关原始发言。已有消息编号、观点编号、作者和 replyTo 可用于定位；选择须考虑最新修正，不凭固定的模型性格标签或支持度决定。
- 选择器只返回一个原参会者、相关消息/观点编号、简短理由及是否需要用户澄清；不代替该参会者生成答案。系统验证参会者和编号确实存在且材料已公开，再调用真实运行时。
- 界面显示「由谁回答」与可展开的选择理由，用户可覆盖。指代含糊且存在多个合理对象时请用户选择；综合方案问题可交给 Leader，并明确说明依据不足时采用了默认策略。
- 初版只需复用本会议的公开记录；长记录可建立带原始编号的主题索引并取回原文，不必先引入向量数据库。没有适用历史时标为新问题，不虚构已有相关分析。

### Leader 兼任路由的早期候选（当前未采用）

此前讨论了让 Leader 兼任 dispatcher。用户随后明确希望增加该角色，提出 Cursor 或 OpenCode 免费模型，并将其命名为 Organizer（会议组织者）。因此以下 Leader 兼任方案仅保留为候选回退方式，不再是唯一建议；当前开发代码采用独立 Organizer：

- 明确点名或引用发言时由代码直接分配；需要理解指代与主题时，才以独立的「路由」任务调用 Leader。这个任务仅给出对象、依据和澄清需要，不同时冒充被分配者回答。
- 可设计主持型 Leader：在轮次边界查看公开材料，指出待解决问题、安排后续回应及负责总结；必要时用户仍可点名 Leader 做分析。单纯观察、主持和总结不计为独立调查报告。若仍需三份独立观点，需要三位 Follower，或让 Leader 另行完成真实独立调查；不能把主持摘要当作第三方研究。
- 不需要常驻调用 Leader 或让其在每条回复后运行。自动路由通常最多一次选择调用，然后一次回答调用；直接点名跳过选择。每轮主持调用与最终总结分别保留真实记录。
- Leader 给出的调度是受校验的建议。参会者身份、原始引用、一次公开发言、轮数上限、暂停和终止由应用代码执行；模型不能突破这些规则，也不能单方面宣称全员同意。
- 小模型可作为后续可替换的路由实现，但须用真实追问和带人工判断的案例比较分配质量、等待时间及调用成本。依据缺失或语义含糊时回退到 Leader 或向用户澄清；不要把模型自报置信度直接当成可靠概率。复杂主持及综合总结仍由所选 Leader 负责。
- 主持角色与讨论角色不要求使用不同底层模型。若同一 provider 分别承担两个任务，记录其真实 provider、模型及任务角色，不将其计为两个独立模型意见。

### Organizer（开发代码已实现，真实接入待验证）

- Organizer 负责观察公开会议记录、安排下一位发言者、依据实际回复分配人类追问、标记需要核查的分歧及提出是否进入总结的建议。dispatcher 是其问题分配职责，不能将其仅作为固定分类器理解。
- Leader 负责综合结论和最终 summary；Follower 负责具体研究、分析、回应与核查。Organizer 的主持信息与研究意见区分，不能将其当作额外一份独立调查。
- 程序仍执行公开发言互斥、轮数上限、暂停与终止。Organizer 的建议需要校验和记录，不能越过用户选择，也不能宣称其他 agent 已开始或完成调用。
- 用户接受新增模型，免费模型候选为 Cursor 和 OpenCode。Organizer 的 provider/model 可替换，不把接入渠道当成模型身份，不把免费模型默认认定为小模型；选择质量、中文指代、结构化输出、耗时和限额均须实测。
- 早期只读核查（安装 Cursor 之前）：Cursor 官方提供 headless CLI，Hobby 为有限 Agent 请求，并非无条件免费 API；本机未发现 Cursor CLI。OpenCode Zen 官方列出限时免费模型及接口，本机 OpenCode 1.18.34 已安装，但 `opencode models opencode` 因数据库缺少 session 表而失败；未发送模型请求，未证明任何免费模型已经接通。不自动修复或清空用户的 OpenCode 数据。
- OpenCode Zen 与付费 Go 区分。免费模型可用期和数据处理条件随模型不同，配置需记录实际来源与模型；自动选择仅在已验证的候选中进行，不静默切换到收费模型。
- 用户没有 OpenCode Go 账号。Organizer 不应要求购买 Go；Zen 虽提供免费模型，官方 API 接入流程仍涉及登录、API key 及账单信息，不能据此声称无需账号或已可调用。可先把 Organizer 设为独立任务角色，复用已有登录的真实 CLI；这不增加独立底层模型数量。无额外订阅的候选接入继续核实。
- 用户提出直接使用 MiniMax API。官方文档确认支持直接文本 API，普通开放平台 API Key 按量使用账户余额，与订阅 Key/套餐额度区分；不依赖 OpenCode Go 或 Cursor。可作为 Organizer 的优先接入候选，但不等于免费或已经接通。模型可用性、中文上下文分配质量、结构化输出与延迟须实际验证；目前未调用 MiniMax。

用户随后安装 Cursor 并指定其为默认 Organizer。Organizer 和 Leader 都可独立选择；Organizer 不参与研究或讨论，Leader 从参会者中选择并负责最终总结。开发代码已提供 Cursor、Codex、Claude、AGY 的 Organizer 候选和角色互斥校验。当前 Cursor CLI 已安装但显示未登录，尚无真实主持成功证据；其他运行时的 Organizer 角色亦待真实调用验证。旧记录不自动加入新角色。

## 0.3.1 回答语言修正

用户反馈中文提问却得到英文回答，要求显示并执行「用提问者的语言回答」。此前随系统策略在英文系统上冻结为英文，构成直接冲突。新会议默认跟随提问，不沿用界面或系统的英文；旧版随系统会议的后续调用也跟随公开问题。所有讨论、独立报告、Organizer 的理由与澄清、Leader 总结和会后回答共用该规则，JSON 字段、编号、代码及原始引用保持原样。界面语言仍独立提供中文、English、随系统；用户明确指定回答语言或在问题中指定其他语言时保留该要求。记录每次调用的语言策略和关联人类消息，不改写已有英文原文。用户进一步要求取消独立 follow-up 页面；公开讨论和总结后提问使用同一个输入框，后续问答在同一条记录中显示，仍保留内部版本与路由证据。
